# 3. 当前安全边界

这是这次重构中最不能破坏的部分。

当前 `ipc.ts` 并不是直接到处裸写：

`ipcMain.handle(...)`

它有统一包装函数 `handle(...)`。

这个包装做两件关键事情：

1. `assertTrustedSender(event, channel)`
2. `sanitizeRendererValue(result)`

即：

所有 renderer 发起的 invoke 都必须先验证 sender/frame/document；

所有结果都必须经过 renderer-safe sanitization。

### 绝对禁止

拆分后任何 domain 文件直接写：

`ipcMain.handle(...)`

这是失败。

任何 domain handler 绕过统一 trusted registrar 也是失败。

任何为了“方便”把 `ipcMain` 传进 domain，让 domain 自己注册也是失败。

正确关系必须保持为：

`Electron ipcMain`
→ `统一可信 registrar`
→ `domain registerXxxHandlers(...)`
→ `业务 handler`

也就是说：

**domain 只能拿到一个已经带安全语义的 `handle` 注册能力。**

domain 不应该拥有 Electron 原始 `ipcMain` authority。

# 6. C# Bridge 是 native authority，不能被这次拆分侵蚀

SoulForge 当前的原则继续保持：

**C# Bridge 是 FromSoftware native binary format 的 production authority。**

TypeScript main 可以负责：

* workspace/session orchestration
* permission boundary
* Patch Engine orchestration
* staging
* renderer-safe projection
* Bridge command orchestration
* IPC lifetime
* UI-facing DTO

但不能为了“减少一次 Bridge 调用”而在 TypeScript 重新实现：

* PARAM parser
* FLVER parser
* BND4 parser
* MSB parser
* EMEVD parser

也不能把 C# 已经解析好的原生 authority 复制成另一套长期存在的 JS authority。

* canonical path 绑定

* Oodle root 进入 key
* LRU/TTL eviction
* source hash stale detection
* parse telemetry

* `pathSourceGeneration`
* `entryIdentity`

除非它直接阻止当前代码编译，否则：

**不要改。**

记录下来即可。

本轮 diff 中：

行为变化越少越好。

# 24. 整体施工顺序

不允许自己重新排序。

完整任务严格按下面顺序执行：

### A0 — 建立不可伪造的 baseline

确认工作树、HEAD、当前构建和生产 IPC contract。

### A1 — 建立最小 registration infrastructure

只抽出 trusted domain registrar 所需的类型/最小基础设施。

### A2 — 先搬低耦合 domain

用低风险模块证明拆分模式正确。

### A3 — 搬 DocumentStore / operations / model services

继续扩大拆分，但不碰最复杂 native editor。

### A4 — 搬 native resource domain

按：

raw/assets/text/map/action

逐个搬。

### A5 — 搬复杂 domain

按：

event → param → workspace → agent

逐个搬。

复杂模块永远后搬，因为这时拆分模式和测试已经验证。

### A6 — 清理跨边界 DTO 的依赖方向

将 preload 仍从 `../main/ipc.js` 引用的纯 IPC DTO 分组搬到 shared。

### A7 — 收缩 composition root

删除已经搬走的 domain cache/helper/import，让 `ipc.ts` 真正变薄。

### A8 — 行为等价总验收

所有 production IPC surface 必须保持。

**只有 A8 全绿才能进入 B。**

# 25. 阶段 B 的目标先记住，但现在不要实施

阶段 B 只处理 PARAM 数据路径。

目标不是“PARAM 改成分页 UI”。

目标是建立：

`Renderer`
→ lightweight PARAM index
→ 按实际 row identity 请求 payload
→ Electron 只转交 opaque documentSession
→ C# session 内同一个 ParamNativeDocument 做 projection

核心数据流最终应接近：

### 打开表

请求 PARAM index：

返回：

* session token
* typeName
* rowDataSize
* sourceHash
* rowCount
* 每行轻量 identity：

  * rowIndex
  * id
  * name
  * 必要时 dataHash

**不返回所有 dataBase64。**

### 用户需要某几行时

renderer 提交：

* opaque document session
* row identities / rowIds（最终物理 identity 规则以后续施工为准）

Bridge 从已经打开的 native document 投影这些行。

只返回这些行的：

* bytes/hash
* field editing 所需 payload

### 搜索

轻量：

id/name 搜索可以基于轻量 index。

如果以后搜索需要字段值：

放在 native/session 一侧执行或做专门索引。

禁止为了搜索再次把整个 PARAM payload 推给 renderer。

# 26. 当前你只需要记住的第一性原则

整个重构只围绕下面五句：

1. **C# native authority 不动。**
2. **Electron IPC 只做控制面和 renderer-safe projection。**
3. **Parse once → Cache native side → Project many。**
4. **大资源 metadata 与 payload 分离。**
5. **先行为等价拆文件，再改变协议。**

如果后面执行过程中出现两个方案不知道选哪个：

优先选择更符合这五条、且改动范围更小的那个。

但是施工图已经确定的地方，不允许重新选方案。

# A1.1 新建文件

---

# A1.2 `registration.ts` 只允许放注册类型

不要把 Electron `ipcMain` authority 放进去。

这个文件只定义 domain 使用的 trusted registrar 类型。

目标形态：

```ts
import type { IpcMainInvokeEvent } from 'electron';

export type TrustedIpcHandle = <Args extends unknown[], Result>(
  channel: string,
  listener: (
    event: IpcMainInvokeEvent,
    ...args: Args
  ) => Result | Promise<Result>
) => void;
```

如果当前 TypeScript 泛型推导因为 strict config 需要略微调整：

允许做最小类型修正。

但是语义不能变化：

domain 最终只能拿：

`TrustedIpcHandle`

不能拿：

`ipcMain`

---

# A1.3 不搬原 `handle(...)`

当前 `ipc.ts` 中原有：

`function handle<...>(...)`

仍然留在 `ipc.ts`。

它继续：

1. 调 `assertTrustedSender`
2. 执行 listener
3. 调 `sanitizeRendererValue`

不要把它挪到 `registration.ts`。

原因：

trusted renderer document 的状态和 Electron raw authority 当前仍属于 composition root。

阶段 A 不扩大 authority。

---

# A1.4 在 `registerIpcHandlers(...)` 内建立 registrar 引用

找到：

`export function registerIpcHandlers(...)`

在它内部原本可以直接使用 `handle(...)`。

增加一个局部 typed alias，例如：

```ts
const trustedHandle: TrustedIpcHandle = handle;
```

如果因为泛型赋值不兼容，不要写 `as any`。

允许使用一个非常薄的 wrapper：

```ts
const trustedHandle: TrustedIpcHandle = (channel, listener) => {
  handle(channel, listener);
};
```

### 禁止

* `as any`
* `as unknown as TrustedIpcHandle`
* domain 自己 import `ipcMain`
* 把 `assertTrustedSender` 复制到每个 domain

# B2. 先解决最危险的问题：PARAM ID 不是物理身份

# B2.1 新协议统一采用 Physical Row Identity

在 shared protocol 中定义：

```ts
export interface ParamPhysicalRowIdentity {
  rowIndex: number;
  id: number;
  dataHash: string;
}
```

三者语义：

### `rowIndex`

当前 native session 内的物理 row ordinal。

### `id`

防止 rowIndex 对应行语义已经改变。

### `dataHash`

防止：

* session 数据过期
* row 被替换
* duplicate ID 下错误 row
* index 与 payload request 不一致

---

# B2.2 三个值必须共同验证

读取 payload 时：

不能：

只检查 `rowIndex`

不能：

只检查 `id`

不能：

只检查 `dataHash`

必须要求：

```text
rowIndex exists
AND actual.id == expected.id
AND actual.dataHash == expected.dataHash
```

不满足任意一个：

整次请求结构化失败。

不要偷偷 fallback 到：

“找另一个相同 id 的 row”。

---

# B2.3 失败代码固定

```text
PARAM_ROW_IDENTITY_MISMATCH
```

错误至少包含 renderer-safe：

* requested rowIndex
* expected id
* actual id，如果可得
* correlationId，如果请求有

* native filesystem path
* stack trace
* raw exception object

不要另发明 MD5/SHA1 等第二算法。

比较：

`actual dataHash`

与：

`expectedDataHash`

不等：

失败。

---

# B4.5 禁止 partial success

假设一次请求三行：

```text

row 2 mismatch
row 3 OK
```

结果必须：

整批失败。

不能：

返回 row 1 和 row 3，再附 warning。

原因：

调用者会认为整个 selection 对应同一个 index snapshot。

---

增加能力：


* rowIndex
* id
* name
* dataHash

以及本来属于 document metadata 的轻量字段。

不能输出：

# B4.7 row hash 必须来自 native parsed document

index response 中：

每个 row 必须有：

`dataHash`

不要让 Node 收到 bytes 后再 hash。

否则又把 payload 拉过 bridge 了。

当 request：

5. 返回 payload

绝对不能：

再在 JSON 层 `.Where(...)`。

否则 native 内存虽然 cache 了，

wire 仍然胖。
