# 一、证据规则

严格遵守以下规则。

## 1. 只有真实运行路径才能证明 First Bad Stage

证据等级：

最高：

真实 SoulForge Electron UI
→ 实际用户操作
→ 实际 IPC
→ 实际 main/core/Bridge
→ 实际 Sekiro / ModEngine 文件
→ 实际返回结果

其次：

同一真实资源通过现有 backend/Bridge 命令直接读取。

不能作为运行时结论：

* 阅读源码
* 单元测试
* mock
* contract test
* synthetic fixture
* 手工构造 JSON
* “理论上会进入这里”
* 根据函数存在推测函数被调用
* 根据日志格式推测真实值
* 旧聊天记录中的结论
* 旧的 `forensics.md` 中没有真实运行支撑的结论

源码只能用于解释观测结果，不能代替观测结果。

---

## 2. UNKNOWN 必须保留为 UNKNOWN

没有观测到的数值禁止写成 `0`。

例如没有成功进入 native FLVER parser：

错误：

`native meshCount = 0`

正确：

`native meshCount = UNKNOWN（未进入 native FLVER parser）`

只有程序实际返回 0，才允许记录 0。

---

## 3. 一旦发现 First Bad Stage，立即停止继续追下游

例如：

`MSB modelName 正确`
→ `mapbnd 解析错误`

那么 First Bad Stage 已经是 mapbnd resolution。

不要继续调查：

* binder entry
* FLVER topology
* renderer
* shader
* camera

本轮目标不是把整条链每一层都分析一遍，而是找到第一次从正确状态变成错误状态的位置。

---

## 4. 不允许修复

发现明显 bug 后也不要改。

只记录：

* 输入是什么
* 输出是什么
* 哪个 stage 首次错误
* 对应源码位置

不要顺手修。

不要创建 commit。

不要 push。

`467 bones / 0 meshes`

* action sourceUri
* relativePath
* derived stem

`derived stem`

`*.chrbnd.dcx`

然后在真实 vanilla / overlay 文件树中确认：

实际 c0000 companion chrbnd 是哪个文件。

必须区分：

而正确的 canonical chrbnd 明确存在，

不要再调查：

* BND entry
* FLVER
* native meshCount
* projection
* skinning
* HKX
* renderer

只有当：

* binder entry 总数
* 所有 FLVER / FLVER.DCX 相关 entry 名
* 实际选择/解析了哪些 FLVER entry

然后进入 Bridge/native parser。

对每个实际解析的 FLVER entry 记录：

* vertex count
* face/index count
* mesh count

再记录：

Bridge DTO 输出：

* mesh 数
* vertex 数
* index 数

再记录 renderer 接收到的：

* mesh 数
* geometry 数

## Step 2：MAPBND resolution

记录：

该 modelName 生成了哪些 mapbnd candidate。

每个 candidate：

* 完整路径
* 是否存在

记录最终 selected mapbnd。

然后判断 selected mapbnd 是否真的属于：

`m10_00_00_00`

以及是否应该包含当前 model。

如果这里错误：

`MAP First Bad Stage = MAPBND resolution`

停止。

## Step 3：Binder entry resolution

只有 mapbnd 正确才进入。

记录真实 mapbnd 内相关 binder entries。

记录代码针对 modelName 生成的 entry variants。

记录最终 matched entry 的：

不要只写：

---

## Step 4：Native FLVER

只有 binder entry 正确才进入。

对实际 matched FLVER 记录 native parser 返回：

* meshCount
* vertexCount
* index/face count

如果 native parser 成功执行且：

`meshCount = 0`

那么：

`MAP First Bad Stage = Native FLVER parse`

如果 parser 根本没有执行：

写 UNKNOWN。

不要写 0。

---

## Step 5：DTO projection

只有 native geometry 明确 `>0` 才进入。

记录：

native：

`mesh / vertex / index`

以及 Bridge/main DTO：

`mesh / vertex / index`

`MAP First Bad Stage = geometry projection`

停止。

---

## Step 6：Renderer

只有 DTO geometry `>0` 才进入。

记录 renderer 实际创建：

* geometry 数
* mesh object 数
* vertex/index 数

如果 DTO `>0` 但 renderer 为 0：

`MAP First Bad Stage = renderer geometry creation`

只有 renderer 已经拥有非零正确 geometry，但画面仍然不可见，才允许进入：

* topology
* winding
* material
* transform
* camera
* clipping

尤其禁止提前重新调查 TriangleStrip。

# 六、ROLLBACK 取证

这是本轮最严格的一项。

不要通过：

* UI 文本
* toast
* audit log 字样

判断 rollback 成功。

必须读取真实 authoritative data。

测试目标：

`ItemName[1000]`

测试修改值：

`苇名国の壶`

如果当前游戏版本不存在该 row，选择另一个真实存在、容易辨认的 ItemName row，并在报告中记录替代原因。

---

## Step 1：PRE authority

在修改前，通过当前系统中最接近 authoritative source 的真实读取路径读取：

* targetUri
* row id
* field
* current value
* source hash

记录为：

`PRE`

这里不能只读取 React state。

优先读取最终会被 commit/patch 操作使用的真实资源状态。

---

## Step 2：通过正常 Agent 产品流程产生修改

必须从真实 Agent 功能发起修改。

不要直接调用底层 patch function 制造 transaction。

目标：

把：

`ItemName[1000]`

改成：

`苇名国の壶`

记录 Agent 最终产生的：

* operation id
* transaction id，如果存在
* targetUri
* targetPath
* beforeHash
* afterHash
* backupPath

不要人为改这些值。

---

## Step 3：commit 后 authority readback

提交完成以后，不看 UI 显示是否成功。

重新通过 authoritative read path 读取同一个：

* targetUri
* row
* field

记录：

`POST_COMMIT`

必须证明其真实值已经是：

`苇名国の壶`

如果 commit 后 authoritative data 根本没有变化，那么 rollback 问题还没有资格调查。

此时记录：

`First Bad Stage = forward commit`

并停止。

---

## Step 4：从真实 Audit/Operation UI 执行 rollback

找到刚才真实产生的 operation。

使用用户实际可见的 rollback 操作。

不要调用内部函数代替。

记录实际传给 backend 的：

`opId`

以及 backend 找到的 original operation：

* targetUri
* beforeHash
* afterHash
* backupPath

确认 rollback 使用的是原 operation identity，而不是重新根据当前 UI 文本猜测目标。

---

## Step 5：rollback 后 authority readback

rollback 返回后，立即重新读取 authoritative data。

记录：

`POST_ROLLBACK_AUTHORITY`

必须读取与 PRE、POST_COMMIT 完全同一：

* targetUri
* row
* field

判断：

是否恢复到 PRE 值。

然后再单独记录：

`POST_ROLLBACK_UI`

即 UI 当前显示值。

---

# 七、ROLLBACK 分类规则

只能根据实际结果分类。

## A：Target Identity Drift

如果 rollback 最终作用的：

`targetUri / resource / row`

不是 forward operation 实际修改的目标：

`First Bad = A Target Identity Drift`

必须给出两边实际 identity。

---

## B：Backend Rollback Semantics

如果 identity 正确，但 backend 构造的 inverse operation 本身语义错误，例如恢复目标值/patch 内容错误：

`First Bad = B Backend Rollback Semantics`

---

## C：Inverse Commit Failure

如果 inverse operation 内容正确，但执行后 authoritative resource 没有恢复：

`First Bad = C Inverse Commit Failure`

---

## D：Authority Restored, UI Stale

如果：

`POST_ROLLBACK_AUTHORITY == PRE`

但 UI 仍显示：

`苇名国の壶`

或其他旧状态：

`First Bad = D Authority Restored / UI Stale`

---

## E：Insufficient Transaction Identity

只有当真实运行证明：

当前持久化记录确实无法唯一找到要恢复的资源/版本，

才允许判定 E。

不能因为：

`transactionId` 是 optional

就直接判 E。

现有：

* opId
* targetUri
* beforeHash
* afterHash
* backupPath

可能已经足够完成文件级 rollback。

必须用实际冲突证明 identity 不足。
