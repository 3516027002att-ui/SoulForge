## T-H1 交接书证据投影改索引行

**用户已裁定采用此方案**,不需要再权衡是否要做,但**怎么做需要判断**。

### 已量清的事实

| 项 | 实测值 |
|---|---|
| 交接书总量 | 449213 B |
| 投影区块合计 | 221105 B(7 处,占 49.2%) |
| `evidence-index` 单块 | 99707 B(22%) |
| `evidence.jsonl` 本体 | 104741 B / 68 条 |
| `result` 正文在交接书原样出现的证据 | 39 条,对应约 51843 B |
| 目标净效果 | 449 KB → 约 364 KB(-19%) |

体量增长轨迹(实测):7-11 = 120 KB → 7-28 = 187 KB → 8-01 = 382 KB → 8-02 = 449 KB。
每次 `gov seal` 追加约 1.5 KB,**所以这是持续增长而非一次性膨胀**。

其余投影区块的体量,供判断边界用:`scope-proposal` 56169 B、`slice-panel` 45694 B、
`gate-matrix` 6753 B、`command-index` 5991 B、`blocker-index` 5983 B、`active-claims` 140 B。
**用户明确只改 `evidence-index`**,其余保持现状,不要顺手一起改。

### 需要你判断的部分

**索引行保留哪些字段。** 用户把这个决定交给工程侧,判据是:

1. 哪些字段实际被读得最多(可查本仓库的提交历史与门禁代码,不要凭感觉);
2. `gov` CLI 是否已投影该字段(已投影的就不必在交接书重复);
3. **门禁是否依赖该字段**——这条最关键,漏掉会让投影压缩把门禁judge的输入抽掉。

候选字段:`evidenceId`、`subject`、`commands`、`result`、`nonClaims`、`gateIds`、
`fingerprint*`、`targetRelease`。至少 `evidenceId` 必须留(它是交叉引用的锚)。

### 必须避开的坑

- **不要手改交接书。** 那 7 处区块在 `SOULFORGE_PROJECTION_BEGIN/END` 标记内,是治理 JSON
  的投影。手写会被投影门禁判为分叉,或另立一份无人校验的口径。改**投影器**。
- **改完必须验证投影门禁仍会红。** 压缩投影时很容易把门禁的判据一起弱化——那就成了
  "只读副本"型假门禁(已实测过:`verify-release-scope.mjs` 曾只解析交接书内嵌 JSON、
  从不读 `docs/governance/scope.json`,27 条 scopeItem 分叉数周而门禁全绿)。
- 投影器是 REL-SCOPE 主题域文件,**先提交再 seal**。

### 验收

- `npm run test:handoff-projection` 与 `test:handoff-integrity` 均绿;
- 给交接书手工注入一处投影区块的改动 → 投影门禁转红 → 还原转绿;
- 报出改前改后实测体量(用 `Buffer.byteLength`,不要用 `wc -c` 混算——两者差约 800 B);
- 68 个 `evidenceId` 在压缩后仍全部可在交接书检索到。

(第 5 条讲的正是这个区别)。

### 第 4、8、9 条的特殊性

它们无机械判据,但**恰恰是最不该丢的三条**:

- **第 4 条(诊断必须指向真实原因)**:这是本仓库最高优先级的约束。指向错误原因的诊断比
  没有诊断更糟——agent 会照着往错误方向修,永远收敛不了,每次尝试烧一整轮上下文。
  已实测修过三处误导型诊断。
- **第 8 条(诚实性)**:没运行的命令、没读的文件、没验证的结论必须明说;
  `unsupported`/`candidate`/`fixture-confirmed`/`partial`/`native-verified`/`blocked`/`unverified`
  严格区分。这条与 `CLAUDE.md` 的硬约束重叠,**先查是否已被 `CLAUDE.md` 覆盖再决定**。
- **第 9 条(流程自优化)**:前八条都是这个循环的产物。丢掉它,约束集就停止演化。

**建议但不强制:** 无机械判据不代表该丢,可能代表"值得为它设计判据"。若你能想出机械判据,
那比并入散文更好——按"让错误不可能发生 > 必然被发现 > 自带修法 > 写进文档"的顺序选。

### 必须避开的坑

- `CLAUDE.md` **被 gitignore**,所以往它写东西进不了新克隆。tracked 的对应物是执行手册。
- 手册当前 20865 B / 10 节,是 agent 必读件。**并入会让它变胖**——挑真正必要的,
  不要把 plan.md 整段搬过去。
- 手册是受管文档,受引用真实性门禁约束:里面写的 npm script 名、node 脚本路径、
  `gov` 子命令必须真实存在。**这两个任务清单也是受管文档**——实测:本条原先用
  `scripts/X.mjs` 当占位符举例,立刻被 `NODE_SCRIPT_MISSING` 拦下。门禁按形状匹配,
  分不清占位符和真引用,所以谈论引用形态时不要写出路径形状的假样例。

## T-H3 交接书是否需要进一步瘦身

**这条是开放判断,允许结论为"不需要"。**

T-H1 做完后交接书约 364 KB。用户已明确**不做**三大投影全改(会到约 277 KB)与按章节拆分。
但如果 T-H1 过程中你发现别的压缩点,可以提出。

### 判断依据

章节维度实测(占总量):§17 实施证据与留痕规则 195940 B(43.6%)、§13 当前技术前沿 86736 B
(19.3%)、§18 V0.5 完成定义 82504 B(18.4%)——**三章占 81%**。

关键权衡:交接书的定位是**人读的完整口径**,而 agent 的入口是 `gov next` + `gov help`
(合计不到 10 KB,有 `HANDOFF_ENTRY_NOT_CLI` 门禁锁定)。所以体量对 agent 的实际伤害
**已经被入口改造缓解了**。继续瘦身的收益要重新论证,不能假定"越小越好"。

### 若要动手

不要重复 T-H1 已覆盖的部分。任何改动都必须:走投影器而非手改、保持投影门禁有效、
给出改前改后实测体量。**结论是"不需要"时,把理由写进本条后删除本条**——那也是一个合格交付。

删完后要确认 `checkedRules` 里没有"声称检查了但已删掉判据"的残留——那正是
"声明与实现分叉"型假门禁。
