# 高难档任务清单(用完即弃)

**本文与 [MECH.md](MECH.md) 同为一次性工作计划,不是长期规范。** 每条做完就删掉那一条;
全部做完连同 `docs/plan/` 整个目录一起删除,退场步骤见 T-H4。

本档的共同特征:**判错不会立刻转红。** 需要跨文件权衡、需要读懂调用链、需要区分
"看起来对"与"真的对"。这些任务中有多条曾因判断偏差在本仓库造成过实际损失。

推进前先读 MECH.md 开头那三条通用要求(负例证明、检查数校验、先提交再 seal),本档同样适用。
**同时读 MECH.md 的「停手线」一节**——那六条不该加门禁的形态在本档同样生效,
而本档更容易犯的是另一类过度工作,见下。

## 本档的过度工作形态:范围扩张,不是门禁堆积

本档任务要求判断,而判断的失败模式是**把判断做大**:读着调用链发现三处别的问题,
顺手都改了;为一个具体需求设计出可扩展框架;把"顺便"做的事写进同一次提交。

现存任务的实际边界:

- **T-H3 的合格交付包含"不需要"。** 已量清 §17/§13/§18 占 81%,若判断当前体量可接受,
  写明理由并删除本条即可。
- **T-H4 只删该删的引用。** 顺手"清理"相邻代码会让这次改动无法审阅——移除门禁本来
  就是高风险动作,混进无关改动等于放弃了 diff 的可读性。

### 三条具体的抑制规则

1. **不要为"将来可能"留扩展点。** 只有一个调用点就写死;只有一种格式就不抽象格式层;
   只有一个块要压缩就不做通用压缩器。本仓库的架构边界(`CLAUDE.md`)要求长期可替换,
   那说的是**已存在的**多实现边界(如 renderer backend),不是给未发生的需求预留接口。
2. **发现的无关问题写进「附:已知债务」,不要顺手修。** 那一节就是为此存在的。
   真实优先级由 `gov next` 决定——顺手修等于自己给自己派活,还绕过了选点权威。
3. **一次任务一次提交。** 本档每条任务的改动都应当能独立 revert。做不到就说明范围扩张了。

### 判断"够了"的标准

不是"还能再改进吗",而是**"这条任务原本要解决的具体问题,解决了吗"**。

## T-H3 交接书是否需要进一步瘦身

**这条是开放判断,允许结论为"不需要"。**

证据索引压缩后交接书约 364 KB。用户已明确**不做**三大投影全改(会到约 277 KB)与按章节拆分。
但如果在证据索引压缩过程中发现别的压缩点,可以提出。

### 判断依据

章节维度实测(占总量):§17 实施证据与留痕规则 195940 B(43.6%)、§13 当前技术前沿 86736 B
(19.3%)、§18 V0.5 完成定义 82504 B(18.4%)——**三章占 81%**。

关键权衡:交接书的定位是**人读的完整口径**,而 agent 的入口是 `gov next` + `gov help`
(合计不到 10 KB,有 `HANDOFF_ENTRY_NOT_CLI` 门禁锁定)。所以体量对 agent 的实际伤害
**已经被入口改造缓解了**。继续瘦身的收益要重新论证,不能假定"越小越好"。

### 若要动手

不要重复证据索引压缩已覆盖的部分。任何改动都必须:走投影器而非手改、保持投影门禁有效、
给出改前改后实测体量。**结论是"不需要"时,把理由写进本条后删除本条**——那也是一个合格交付。

## T-H4 `docs/plan/` 自身退场

**这是两档合起来的最后一条,不只是本档的最后一条。**

它删除 `docs/plan/` 整个目录,**包含 MECH.md**。所以无论两档谁先做,
T-H4 都必须等到 MECH.md 的条目也全部清空(全部完成或明确判定不做)才能执行——
见下面退场步骤第 1 步。若本档先推进,清空 T-H4 之前的高难档条目后就**跳过 T-H4 并停手**,
把它留给机械档的收尾者;或等机械档跑完后再回来做。

误判成"本档最后一条"的后果:删掉一份别人还没做的任务清单,而它不在 Git 历史之外的
任何地方——机械档 agent 会拿不到自己的输入。

### 已经拆掉的部分(不要重做)

单文件时期本目录被焊成硬依赖:`PLAN_MISSING` 会在文件缺失时报 error,于是
**删掉用完即弃的文件反而让治理层转红**。实测确认过(移走 `docs/plan.md` 立刻
报 `PLAN_MISSING` + `DEAD_LINK`),已于拆分时修掉:

- `PLAN_MISSING` 已移除;
- 两档清单改为 `MANAGED_DOCS` 的**可选成员**——存在就纳入扫描,删掉自动退出集合;
- 条目交叉引用门禁从校验「第 N 条」改判任务 ID(`PLAN_SECTION_REF_DANGLING`
  → `PLAN_TASK_REF_DANGLING`),因为失效方式变了:从「插入条目顶掉后续编号」
  变成「做完删条目导致别处引用悬空」。

所以现在删除 `docs/plan/` 只会得到 **2 条 `DEAD_LINK`**(README 那两行),
不会有文件缺失类错误。这一点已实测。

### 退场时仍需一起拆掉的引用

| 位置 | 内容 | 不拆的后果 |
|---|---|---|
| `scripts/verify-handoff-integrity.mjs:26-27` | `PLAN_HARD` / `PLAN_MECH` 常量 | 死代码,无门禁后果 |
| 同文件 41-42、51-52、70-71 行 | 读取与两处可选成员展开 | 死代码 |
| 同文件 `PLAN_TASK_IDS_UNPARSEABLE` / `PLAN_TASK_REF_DANGLING` | 任务 ID 引用校验 | 判据对象消失(空集时自动跳过,不转红) |
| 同文件 `checkedRules` 末条 | 声明该规则被检查 | **声明与实现分叉** |
| `README.md:122-128` | 「一次性任务清单」整节 | **`DEAD_LINK` ×2** |

行号是 2026-08-02 实测值,**动手前重新 grep 确认**——文件会变。

### 退场步骤

1. 确认 HARD.md 与 MECH.md 里所有任务条目都已删除(即全部完成或明确判定不做);
2. 删除 `docs/plan/` 整个目录;
3. 从 `verify-handoff-integrity.mjs` 移除上表前四行(含 `checkedRules` 那条声明);
4. 从 `README.md` 移除「一次性任务清单」整节,包括那段解释 `DEAD_LINK` 的说明;
5. 跑 `node scripts/verify.mjs --tier governance`,必须全绿;
6. 走封存四步。

### 为什么这条归高难档

移除门禁比添加门禁更容易出错:**留一处引用就转红,删多了则悄悄失去覆盖。**
删完后要确认 `checkedRules` 里没有"声称检查了但已删掉判据"的残留——那正是
"声明与实现分叉"型假门禁。第 3 步删掉的两个门禁码要顺手在仓库里全局搜一遍,
确认没有别处(fixture、文档、注释)还在声称它们存在。
