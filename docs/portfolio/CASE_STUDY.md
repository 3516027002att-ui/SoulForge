# SoulForge：面向复杂 Mod 的 AI 原生工程工作台

## 一句话介绍

SoulForge 把传统的“解包—切换多个工具—依赖经验修改—手工恢复”改造成一条可解释、可验证、可回滚的工作流：用户用自然语言描述目标，Agent 在当前 Mod 工作区中定位资源、读取原生证据、生成 Patch 方案，并在权限和 Patch Engine 约束下提交。

## 1. 用户问题

复杂 Mod 的时间成本不只来自“修改一个值”，还来自上下文切换和隐性知识：

- 先解包，再在多个查看器、参数编辑器、脚本工具和地图工具之间切换；
- 不同资源之间存在串联、并联、引用和触发关系，新用户很难判断下一步应该查什么；
- 工具的交互范式仍然接近二十年前的编辑器，无法利用当下 AI 的自然语言理解、工具调用和自动化能力；
- 一旦修改错误，恢复依赖人工记忆，复杂任务很难知道影响面和回退范围。

我把问题定义为：

> 如何让 Mod 创作者用一句话表达目标，同时仍然看得见证据、知道影响面、能控制每一步，并且在失败时安全回到修改前？

## 2. 产品定位

不是“让 AI 随便改游戏文件”，而是：

> 面向 FromSoftware Mod 工作区的 AI 协作编辑器。

它的核心价值是降低领域工具的学习门槛，但不牺牲原生格式边界、用户确认和可恢复性。

## 3. 核心体验闭环

```text
自然语言目标
  -> 工作区索引与证据检索
  -> 原生读取确认当前值
  -> 生成 Patch proposal / 影响图
  -> 风险与格式校验
  -> 用户审批
  -> Patch Engine staging
  -> 备份、原子提交、写后重读
  -> 操作日志与可回滚
```

Agent 的角色类似 coding agent，但领域工具是 Mod 资源工具：

- `workspace_stats`：确认当前工作区和索引规模；
- `retrieve_evidence`、`search_param_rows`、`search_events`、`search_map_entities`：定位候选证据；
- `read_param_fields`、`read_emevd_outline`、`read_msb_parts`、`read_tae_events`：读取原生对象；
- `build_patch_graph`、`validate_patch`、`assess_edit_risk`：生成并检查变更方案；
- `commit_patch`、`rollback_operation`：经权限和 Patch Engine 执行提交或恢复。

## 4. 关键架构判断

### 4.1 为什么默认使用 lexical 证据检索

这类语料和通用知识库不同，主要信号往往是：

- 精确数字 ID；
- 参数表、字段名和资源路径；
- 事件、动作、地图对象等稳定符号；
- 一跳引用关系。

因此默认采用本地 lexical + 结构化 ID + 引用扩展，而不是把每次检索都建立在外部 embedding/API 能力上。这样有四个好处：

1. 对用户的 API 能力要求更低；
2. 结果可以解释为“命中了哪个 ID、路径或引用”；
3. 查询成本稳定，适合桌面端和长任务；
4. 原生读取仍然负责最终确认，检索不会越权成为写入依据。

代码中的 `RagCorpus` 是历史内部命名；产品口径以“本地证据索引 / lexical 检索”为准，不把向量相似度当成事实置信度。

### 4.2 为什么不把一个模型硬编码到底

开发协作阶段根据任务混合使用：

| 任务 | 选择依据 | 参与过的模型池 |
| --- | --- | --- |
| 复杂方案、架构和代码审查 | 推理深度、长上下文、稳定性 | Opus 5、GPT-5.6 Sol |
| 快速定位、交互和低成本迭代 | 延迟、价格、可用额度 | Luna、Grok 4.5/4.6、GLM 5.3、Flash、DeepSeek V4 Flash |
| 综合任务 | 成本与效果的折中 | Qwen 3.8 Max 混合 |

运行时不把这些模型名写死：用户可配置自己的 API、协议、模型和思考强度。产品的价值在任务编排、证据边界和验证机制，而不是绑定某一家模型。

### 4.3 为什么写入必须分层

模型输出只能是候选方案，不能直接成为生产资源。写入前必须完成：

1. 读取当前原生值和 `sourceHash/sourceRevision`；
2. 生成 typed mutation 或 PatchIR；
3. 校验字段类型、范围、资源关系和风险；
4. 经过用户审批或受控权限策略；
5. 由 Patch Engine 写入 staging，备份后原子提交；
6. 写后重读，失败时结构化报错并回滚。

这使“AI 说它改好了”和“文件确实被安全修改且可以恢复”成为两个不同的产品状态。

## 5. 真实实践证据

仓库已经保留本地 Agent 会话归档，当前索引记录 45 个会话。一个典型复杂任务是：

> 修改鬼刑部：从 BOSS 改为精英怪，掉落物品增加一个靛蓝星陨，红点数改为 2。

最长一条归档记录为 64 步。它适合展示的不是“模型一次就答对”，而是：

- 先确认工作区范围；
- 通过文本和参数证据逐步定位；
- 处理多资源之间的关联；
- 在发现失败时切换定位路径；
- 区分候选证据、原生读取和可写依据；
- 记录每轮工具调用，便于复盘产品设计和失败原因。

## 6. 迭代前后对比怎么讲

作品演示时不把“迭代”伪装成虚构增长数据，而是展示任务轨迹和行为变化：

| 迭代对象 | 之前 | 之后 |
| --- | --- | --- |
| 工具调用 | 模型容易猜参数名或重复失败 | 工具 schema 投影、结果 envelope 和语义重复失败预算更明确 |
| 任务状态 | 用户难以知道 Agent 是否卡住 | 有运行、重试、压缩、审批、取消、错误和部分完成状态 |
| 检索 | 依赖用户理解资源组织方式 | 先用 lexical、ID 和引用关系降低定位门槛 |
| 写回 | “模型说改了”与实际文件状态混在一起 | 提案、校验、审批、提交、重读和回滚分层 |
| 追责 | 失败难以复盘 | 会话和工具调用可回看，错误参数不静默隐藏 |

明天拿到测试集后，再补充定量评估：命中率、错误定位率、重复工具失败率、单任务调用步数、写回前拒绝率和回滚成功率。当前不提前填数字。

## 7. 明确边界

当前没有提供像 Blender 那样自由操控 3D 模型和地图界面的 Agent 接口。要做到这一点，需要额外处理场景状态同步、几何和骨骼语义、交互投影、渲染状态以及模型可靠性，工作量和风险都明显超出当前闭环。

现阶段只展示已经具备证据的能力：结构化地图查询/变换边界、资源定位、原生读取、Patch 计划、受控写回、验证和回滚。3D 自由操控作为后续方向，不作为本次作品的完成声明。

## 8. 一分钟总结

SoulForge 的产品判断是：

> 用 AI 降低 Mod 工具的学习门槛，用 lexical 证据和原生读取保证可解释性，用 Patch Engine、审批、验证和回滚保证可控性。

这不是给旧工具套一个聊天框，而是重新设计“人、模型、领域工具和风险边界”之间的协作关系。
