# SoulForge 作品演示脚本

建议录制 3–5 分钟。语速正常，展示真实 UI 和真实任务轨迹，不要把没有验证的结果说成已经完成。

## 0:00–0:25：先讲问题

“以前改一个复杂 Mod，往往要先解包，再在参数、文本、事件和地图工具之间切换。最难的不是改某个数字，而是知道这个数字属于什么资源、会影响什么，以及失败后怎么恢复。SoulForge 想解决的是这条工作流，而不是再做一个孤立的编辑器。”

## 0:25–0:55：展示产品定位

打开 SoulForge，展示：

- 当前 Mod 工作区；
- 资源索引和编辑器入口；
- 右侧 Agent 面板；
- 模型服务配置入口。

说：

“用户可以用自然语言表达目标。Agent 负责定位和编排，但写操作仍然受证据、权限和 Patch Engine 约束。”

## 0:55–1:55：跑一个真实任务

输入：

```text
修改鬼刑部：从 BOSS 改为精英怪，掉落物品增加一个靛蓝星陨，红点数改为 2。
```

重点展示 Agent 的顺序：

1. `workspace_stats`：确认当前工作区和索引；
2. lexical / ID / 引用检索：找到候选参数和文本；
3. 原生读取：确认当前值、来源和版本；
4. Patch graph：说明可能涉及的跨资源影响；
5. 校验：检查类型、范围和前置条件；
6. 审批：停在用户确认，而不是直接落盘。

旁白：

“这里的 lexical 检索不是把自然语言丢给一个黑箱向量库。Mod 场景中数字 ID、路径、表名和符号非常重要，所以先用本地词法和结构化索引命中，再通过原生读取确认。模型只负责理解、规划和调用工具。”

## 1:55–2:30：展示可控性

展示任务面板中的：

- 当前模型服务；
- 工具调用记录；
- 重试或错误诊断；
- 审批卡片；
- 取消任务按钮；
- 会话历史。

旁白：

“Agent 不是越自动越好。长任务有步数上限，工具失败有重复语义预算，写操作有审批，用户可以取消，结果和失败原因都会进入会话记录。”

## 2:30–3:05：展示模型架构判断

打开模型服务设置，说明：

“开发阶段我根据复杂度、成本和延迟混合使用 Opus 5、GPT-5.6 Sol、Luna、Grok 4.5/4.6、GLM 5.3、Flash、DeepSeek V4 Flash 和 Qwen 3.8 Max。这里不把模型写死，用户可以配置自己的 API。模型是可替换的推理层，稳定的产品能力来自工具 schema、证据边界和验证闭环。”

注意：不要在没有实际联网验证的情况下声称每个模型都已成功调用；只说它们是开发协作/候选模型池。

## 3:05–3:35：讲清楚边界

“当前没有实现像 Blender 那样自由操控 3D 模型和地图。这个能力需要场景状态同步、几何和骨骼语义、渲染投影以及更高的模型可靠性，不能为了让 Demo 看起来完整而假装已经解决。当前版本优先保证资源定位、原生读取、受控写回、验证和回滚。”

## 3:35–4:00：结尾

“SoulForge 的核心不是让 AI 替用户做所有决定，而是让复杂 Mod 的专业工作变得更容易进入、更容易解释、更容易验证，也更容易安全恢复。”

## 面试追问备答

### 为什么不用纯 RAG？

“我观察到目标用户的 API 和设备能力差异很大，而 Mod 语料又高度依赖精确 ID、资源路径和字段名。默认 lexical 更便宜、更透明、更容易失败关闭；未来可以把语义检索作为可选增强，但不能让它成为事实或写入依据。”

### 为什么不让 Agent 直接改文件？

“因为模型输出和生产资源状态不是一回事。必须先有原生读取、typed mutation/PatchIR、验证、审批、staging、备份和写后重读；任何一步不满足，就返回结构化诊断。”

### 你如何证明产品真的有效？

“我会用明天给出的测试集做可重复评估，指标包括检索命中、原生确认、重复失败、任务步数、拒绝率和回滚结果；在数据出来前不填虚构的提升百分比。”

### 为什么不做 Blender 式 3D Agent？

“因为那不是加一个按钮，而是要解决语义场景状态、交互同步和模型可靠性。当前先收敛在能够真实验证的结构化编辑闭环，边界写清楚比展示一个不可靠的 3D 假能力更重要。”
