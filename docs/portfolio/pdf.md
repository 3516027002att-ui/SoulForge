## 一、整份 PDF 的叙事主线

> 复杂 Mod 修改的核心难点，在于先将需求目标对应到项目内的实际对象，再把跨文本、参数、物品、地图、事件和脚本的影响关系完整展开。

SoulForge 正是把这段隐性工作编排成 Agent 流程：

> 用户目标 → 目标对象 → 工具搜索 → 跨文件关系扩展 → 格式化 Evidence → 修改路径 → 用户确认 → 受控写入

### 全文固定用词

- 如果展示错误指令，写作“把鬼型部误写成鬼刑部”，不能反过来把真实目标写成鬼刑部。
- 示例mod为孑影长荫
- 使用“修改链路”“Agent 流程编排”“Evidence 台账”“写入门禁”等产品语言。
- 提效数据只采用简历、代码和测试记录中有来源的工程测量；区分 Mod 工具链提效与 AI Native 研发提效，不把不同条件下的会话步数直接写成 KPI。

### 第 2 页：用户问题

**页面标题**

> Mod 修改的时间成本，主要花在定位和切换

**开场文案**

> 以前修改一个复杂 Mod，通常要先解包，再在参数工具、文本工具、事件工具和地图工具之间反复切换。用户知道想要的结果，却不一定知道它对应哪个文件、哪个字段或哪条事件。

**三块问题卡片**

#### 1. 上下文被工具切断

解包、查找、编辑、打包分别发生在不同工具中。用户的目标、当前对象和上一轮结果无法自然传递。

#### 2. 资源之间存在隐性关系

一个看似简单的改动，可能同时涉及参数表、物品文本、地图和事件多文件联动，学习门槛较高
#### 3. 现有工具没有利用 AI 的工作方式

成熟工具仍以较早期的编辑器交互为主；对工作效率提升有限，且学习门槛较高。

**底部结论**

> 用户需要一条低门槛的，把自然语言目标连接到正确资源和修改路径的工作流。

**视觉构成**

传统流程横向展开：

> 解包 → 参数编辑器 → 文本工具 → 事件工具 → 打包 → 进游戏测试

在工具节点之间突出“重复查找”“上下文丢失”“需要经验”三个摩擦点。

### 第 3 页：产品定位

**页面标题**

> 从普通编辑器到 Mod 修改 Agent

**产品定位**

> SoulForge 是面向复杂 Mod 工作区的 Agent 流程编排工具：用户描述目标，Agent 负责解析、检索、判断路径并组织领域工具完成修改。

**Agent 处理的任务对象**

- 用户目标：想让什么发生变化；
- 修改意图：属性调整、奖励增加、事件行为变化等；
- 目标对象：NPC、物品、文本、参数表、事件和资源文件；
- 资源关系：参数字段指向的掉落表、物品、地图实体、事件和脚本；
- 不确定性：名称错误、语义模糊、项目内知识缺失；
- 修改路径：参数、掉落表、事件或多个资源的组合；
- 输出方案：涉及对象、当前值、目标值、关联资源、影响范围和待确认项。

**页面中心句**

> 模型负责理解，规划，领域工具负责搜索、读取、验证和执行。

**视觉构成**

左侧放用户输入，右侧放 Agent 输出的结构化任务卡：

```text
目标对象：鬼型部 / 靛蓝星陨
修改意图：精英化 / 增加奖励 / 红点数改为 2
可能资源：NpcParam / EquipParamGoods / EMEVD
待确认：红点对应字段、奖励发放路径
```

### 第 4 页：修改链路

**页面标题**

> 可靠的修改链路工作流

**主流程**

```text
用户描述需求
  → Agent 解析目标与修改意图
  → 在文本和参数中寻找最相关名称
  → 定位 ID、字段和资源
  → 扩展跨文件引用和影响关系
  → 对所有关联对象做原生读取确认
  → 判断参数、掉落表还是事件路径
  → 编写格式化 Evidence
  → 生成修改方案和影响范围
  → 用户确认
  → Patch Engine 受控写入
  → 写后读取、操作记录和必要的回退
```

**每一步页面短文案**

1. **解析**：把用户需求拆成目标对象和修改意图；
2. **搜索**：先查最相关的名称、ID、字段和资源；
3. **关系**：从参数、物品、文本、地图、事件和脚本之间展开引用边；
4. **确认**：对目标和关联对象做原生读取，确认当前值、来源和关系；
5. **判断**：识别必要的修改对象和修改方式；
6. **成案**：用 Evidence 固定搜索结果和关联边，再形成修改方案；
7. **执行**：用户确认后交给写入工具和 Patch Engine；
8. **收口**：记录结果，失败时输出结构化诊断并按流程回退。

**页面要证明的能力**

这是一套有阶段、有工具、有状态、有跨文件影响闭包和写入门槛的 Agent 流程。

### 第 6 页：三类复杂指令

**页面标题**

> 三种指令不确定性，分别需要不同的检索动作

本页三个大标题固定为：**错误指令、模糊指令、知识外指令**。

#### 错误指令

Demo 可加入一个错误变体：把“鬼型部”误写成“鬼刑部”。Agent 不能把错误名称直接当成另一个对象，也不能擅自把用户的真实目标改成错误写法；它要搜索项目中的名称、别名和相关资源，确认最终目标仍是鬼型部。

#### 模糊指令

“红点数改为 2”不是一个天然明确的字段名。模型大概率不知道“红点”在这个项目里具体指什么，必须结合参数说明、项目文本、历史 Agent 对话和开发记忆提出候选解释。

页面可展示候选：

- `NpcParam.ninsatuNum` 当前记录值为 3，可能与处决次数/血条段数有关；

#### 知识外指令

“靛蓝星陨”不是只狼原版知识，而是 Mod《孑影长荫》中的原创忍具。Agent 需要在项目自己的文本、参数、事件、历史对话和开发记忆中找到它。

**页脚结论**

> 名称核对、语义解释和项目知识发现，不能用同一种搜索动作替代。

### 第 9 页：记忆与检索系统

**页面标题**

> 记忆与检索系统

**记忆内容覆盖**

- Mod 文本；
- 参数说明；
- 物品文本；
- 事件文本；
- Agent 历史对话；
- 操作记录；
- 项目知识；
- 开发记忆。

**检索策略**

> **默认采用 lexical + 结构化检索，而不是依赖 embedding / RAG。**

**选择理由**

- SoulForge 面向真实 Mod 用户，而不是熟练调用 API 的 AI 开发者，根据调用，目标用户大概率不会配置embedding模型；
- 降低额外模型调用与 Token 成本；
- 对 ID、名称、字段、参数表等高度结构化对象，关键词与结构化检索本身具有很强价值；
- 检索结果先进入 ID、引用和 `crossReferences` 的关系扩展，再形成格式化 Evidence；
- 后续 Agent 决策和写入均基于对象与关系共同构成的证据链；
- 模型负责理解与规划，确定性工具负责搜索、验证和执行。

**可选增强**

用户可以主动配置 embedding 以开启 RAG，提高搜索效率。工程实现保留 Embedding + RRF 混合召回作为配置增强；未开启时，软件仍通过 lexical、结构化字段、ID 和引用关系编排高效搜索流程。

**运行规则旁注**

用户记忆中的成熟写入规范属于每次任务完整注入的操作规则，不属于 RAG；每次 Agent 运行都全量写入系统提示词。写入路径由代码挂钩 Evidence 文件，Evidence 文件的写入强制依靠工具搜索结果。

**本页要证明的产品判断**

> 我没有因为“RAG 是 AI 产品标配”就直接采用 RAG，而是根据用户能力和任务结构选择了更合适的默认检索方案。

**视觉构成**

左侧是八类项目记忆，右侧是两条路径：

```text
默认：lexical + 结构化检索 → 关系扩展 → Evidence
可选：配置 embedding → lexical / 结构化 + RAG → 关系扩展 → Evidence
```

两条路径最后都汇入同一个 Evidence 和写入门禁，不画成两个事实来源。

### 第 10 页：Evidence 与写入门禁

**页面标题**

> Evidence：把搜索结果接到写入工具的中间接口

**定义**

Evidence 是 Agent 根据工具搜索结果编写的格式化文本文件，既记录待写对象，也记录已经确认的关系边。它不是模型隐藏上下文，也不是向量本身。

**词条与修改次数**

写入工具检测 Evidence 中是否存在与 edit target 对应的资源词条，词条匹配不区分大小写；词条后的数字是本轮允许消耗的修改次数。每次通过写入都会消耗一次，若要继续修改，必须回退已消耗次数，或重新调用搜索工具、由 Agent 更新 Evidence 后再写入。

**固定流程**

```text
Agent 列出目标对象
  → 调用搜索工具
  → 搜索工具返回 searchId 和结果
  → 沿 ID、refs、sourceUri 和 crossReferences 扩展关联对象
  → 原生读取所有关联对象
  → Agent 根据搜索结果编写 Evidence 文本文件
  → Agent 形成修改方案
  → 用户确认
  → 写入工具检测每个待写对象和必要关联词条
  → 有完整词条才允许通过，并消耗对应词条的修改次数
```

**鬼型部任务的 Evidence 示例**

```text
# Evidence

## Target
- 鬼型部
- 靛蓝星陨

## Evidence entries
- npcparam（3）：NpcParam 50800000；ninsatuNum 当前为 3。
- msb（1）：characterId c5080 → m11/m13 地图实体，关联对象已原生读取。
- emevd（1）：m11_00_00_00.emevd.dcx 中的 11105800/11105810/11105900/11105910 事件关系已确认。
- itemlot / equipparam_goods（1）：奖励入口与 Goods 5970 的关系已原生确认。
```
**页面要表达的技术判断**

> 写入工具检测每个 edit target 是否有对应 Evidence 词条；如果关系扩展发现存在关联对象，关系词条和关联对象的原生读取也必须齐全，否则拒绝写入。Evidence 是写入授权的必要接口，具体资源工具再负责字段类型、ID 合法性和原生格式处理。

### 第 11 页：Agent 工作链路提效

**页面标题**

> 一句话需求，Agent 跑完一条可验证的修改链路

**开场说明**

本页只采用已有数字记录的四个环节：资源检索、事件读取、长脚本首屏和原生验证。跨文件关系扩展是必经链路节点，但没有独立测量数字，因此不为它编造效率指标；自然语言解析、Evidence 判断和写入门禁同样只作为链路节点展示。

**Agent 工作链路**

```text
用户描述目标
   ↓
Agent 解析目标与修改意图
   ↓
搜索工具定位文本 / 参数 / 物品 / 事件
   ↓
扩展跨文件引用与影响范围
   ↓
Agent 根据搜索结果编写格式化 Evidence
   ↓
Agent 判断修改路径与影响范围
   ↓
用户确认
   ↓
Evidence 门禁 + Patch Engine 受控写入
   ↓
原生重读与结果验证
```

**Agent 工作链路的可量化提效**

- 资源检索效率提高 37.69 倍；
- 事件读取速度提高 100%+；
- 长脚本首屏负担降低约 99.4%；
- 原生结果验证加速 32.3 倍。

### 第 12 页：真实迭代、范围与结尾

**页面标题**

> 从反复试错的会话记录，提炼出可复用的 Agent 流程

**会话证据的使用方式**

项目归档中同一类“修改鬼型部”任务出现过 64、19、9、4 等不同步数的会话记录。它们的模型、索引状态、工具权限和运行阶段并不完全相同，因此不能简单写成“64 步降到 4 步”的前后实验；本页用它们展示问题如何暴露、流程如何被产品化。

**从会话暴露的问题到产品机制**

| 会话中暴露的问题 | 从记录提炼出的产品机制 |
| --- | --- |
| 名称可能写错，搜索沿着错误称呼反复尝试 | 先登记目标对象，再用项目搜索确认真实对象 |
| 中文未命中后继续猜 ID 和字段 | lexical、结构化字段和引用关系分层检索 |
| “红点”容易被模型直接猜成字段 | 保留候选解释，证据不足时进入待确认 |
| 忍具卷轴和忍具本体容易混淆 | 区分 `Goods 5970` 与 `Weapon 78600` |
| 参数已改但关联事件未知 | 参数命中后强制扩展跨文件关系；关系未闭合时禁止写入 |
| 事件只返回摘要或截断结果 | 关联事件必须完成原生读取，不能用摘要代替写入依据 |
| 模型输出和文件修改混在一起 | 搜索、Evidence、写入门禁、Patch Engine 分层 |

**最近测试暴露的技术债（已纳入修复）**

真实 Agent 记录中曾出现过三种连续形态：

- `gyoubu-elite-indigo-field-refs-2026-09-02T15-29-23-972Z.json` 的 `analysis.references=0`，工具序列没有事件检索，却直接修改了 `NpcParam 50800000` 的 `ninsatuNum` 和 `itemLotId_1`；链路在参数 / 掉落表层提前结束。
- `gyoubu-elite-lightning-bell-v7-2026-09-03T00-54-09-792Z.json` 已提交参数修改，但 `DisplayBossHealthBar`、`SpawnMapSFX` 和奖励路径仍未闭合，任务最终为 `partial`。
- 后续 `real-agent-2026-09-03T09-31-55-194Z.json` 与 `gyoubu-team-real-2026-09-03T10-34-51-792Z.json` 已发现 `c5080 → MSB → EMEVD`，但事件体仍是截断投影，未完整消费就只能停在写入前。

这说明技术债不在于某一个字段查不到，而在于参数命中后没有强制把可达的事件、地图、物品和脚本关系展开成完整闭包，导致参数可能先被修改，关联逻辑却尚未确认。

**修复后的产品机制（最终口径）**

- 搜索命中后，Agent 沿 `ID`、`refs`、`sourceUri` 和 `crossReferences` 展开所有相关文件，形成对象与关系边的集合；
- 关系集合覆盖文本、参数、物品、地图、事件和脚本，所有关联对象都必须完成原生读取；
- Evidence 同时记录待写对象、关联对象、关系边和修改次数；写入工具检测目标词条及其必要依赖，任一关联关系未闭合就拒绝写入；
- 用户确认后，Patch Engine 对已闭合的影响范围统一暂存、写入、重读并记录操作与回退结果。

**会话记录中已经确认的关键链路**

- `NpcParam 50800000` 对应鬼型部，`ninsatuNum` 当前为 3；
- `Goods 5970` 是“忍具卷轴·靛蓝星陨”，`Weapon 78600` 是制作卷轴后得到的忍具本体；
- `NpcParam 50800000` → `characterId c5080` → `m11/m13` 地图实体 → `m11_00_00_00.emevd.dcx` 中的 Boss 事件；
- `itemLotId_1~6` 为空时，奖励不能停留在普通 NPC 参数掉落，必须继续检查 ItemLot 或事件发放路径；
- 这些结论来自工具搜索和参数、文本、地图、事件读取记录；最终写入必须在全链路原生读取完成后进行，不用成功文案覆盖未完成步骤。

## 三、制作执行规范

### 每页固定结构

- 顶部：页码 + 页面标题；
- 中部：一个真实流程、表格或 Evidence 示例；
- 右下角：本页结论；
- 视觉元素必须服务于页面结论，避免堆叠代码截图。

### 截图与对话摘录

- 优先使用真实 Agent 会话中的搜索结果、参数读取和事件路径；
- 长对话只截取“输入 → 搜索失败/命中 → 关键判断 → 下一步”的连续片段；
- 所有截图中的名称统一校对为“鬼型部”“靛蓝星陨”“孑影长荫”；
- 需要展示未完成或失败时，保留结构化错误，不用成功文案覆盖。

### 不放入 PDF 的内容

- 未实测的模型排名和胜率；
- 虚构的效率提升数字；
- 将 Evidence、日志或 synthetic 测试写成完整游戏内写回；
- 将 3D 地图自由操控写成当前功能；
- 大段代码、完整工具 schema 和与主线无关的架构细节。
